# AGENTS.md

Этот файл действует для всего репозитория.

## Назначение проекта

Проект — ядро Hide and Seek для Counter-Strike 1.6, реализованное одним Pawn-плагином AMX Mod X. Не превращайте ядро в монолитную серверную сборку: anti-frag, статистика, movement-механики, карты и административные функции должны оставаться отдельными плагинами, пока утверждённый OpenSpec change явно не меняет эту границу.

## Источники истины

Используйте их в таком порядке:

1. `openspec/specs/**/spec.md` — нормативное актуальное поведение.
2. `openspec/changes/<change>/` — согласованная дельта активного изменения.
3. `src/scripting/hns.sma`, `src/configs/hns.cfg`, `src/data/lang/hns.txt` и тесты — фактическая реализация.
4. `README.md` — инструкция для владельца сервера и разработчика.

Если код расходится со спецификацией, не выбирайте молча одну из сторон. Установите фактическое поведение, отразите решение в текущем OpenSpec change и синхронно обновите код, тесты и пользовательскую документацию.

## Обязательный OpenSpec workflow

Все нетривиальные изменения проходят через OpenSpec, включая исправления багов и изменения конфигурации.

1. Перед планированием прочитайте `openspec/config.yaml` и относящиеся к задаче спеки.
2. Исследование без реализации выполняйте через `openspec-explore`.
3. Создайте change через `openspec-propose`; не начинайте менять продуктовый код до готовности proposal/specs/design/tasks.
4. Реализуйте задачи через `openspec-apply-change`, сохраняя изменения атомарными.
5. Запустите тесты, компиляцию Pawn и `openspec validate --all --strict`.
6. Синхронизируйте и архивируйте завершённый change через `openspec-sync-specs`/`openspec-archive-change`.

Чисто документационное или инфраструктурное изменение без изменения поведения всё равно оформляйте change. Для него допустим `skip_specs: true`, если основные спецификации действительно не меняются.

Не редактируйте сгенерированные `.agents/skills/openspec-*/SKILL.md` вручную. Обновляйте их официальной командой `openspec update` и проверяйте получившийся diff.

## Карта репозитория

- `src/scripting/hns.sma` — вся игровая логика.
- `src/configs/hns.cfg` — поставляемые значения Cvar; файл хранится в CP1251.
- `src/data/lang/hns.txt` — словарь всех пользовательских сообщений, UTF-8.
- `src/sound/hns/` — обязательные countdown/falldown WAV и один пока неиспользуемый start asset.
- `tests/test_hns_source.py` — статические регрессионные проверки Pawn-кода и ресурсов.
- `openspec/specs/` — актуальные capability specs.
- `openspec/changes/` — планируемые и архивные изменения.

## Правила изменения Pawn-кода

- Целевая и проверяемая версия — AMX Mod X 1.10.
- Сохраняйте существующий Pawn-стиль и табуляцию в `hns.sma`, даже если общий `.editorconfig` задаёт пробелы.
- Учитывайте лимит игроков 1–32 и проверяйте границы entity/player-массивов до обращения по индексу.
- Каждой группе отложенных задач выделяйте отдельный диапазон task ID. Удаляйте задачи при disconnect, завершении раунда и смене состояния, если callback больше не должен выполняться.
- Не добавляйте тяжёлые полные обходы игроков/сущностей в частые forwards (`FM_Think`, `FM_CmdStart`, сообщения) без обоснования в `design.md`.
- Всё, что требуется клиенту во время карты, должно быть precache в `plugin_precache`. Изменение путей звуков требует смены карты.
- Новый Cvar добавляйте согласованно в enum/регистрацию, `hns.cfg` при необходимости, README, соответствующую спецификацию и тесты.
- Не встраивайте видимые игрокам строки в Pawn. Добавляйте одинаковые ключи в `[ru]` и `[en]` файла `hns.txt`, сохраняя одинаковые format placeholders.
- Не добавляйте функциональность anti-frag в ядро без отдельного решения, меняющего `core-boundaries` spec.

## Кодировки

- `hns.sma`, `hns.txt`, Markdown, YAML и Python — UTF-8.
- `src/configs/hns.cfg` — CP1251. Читайте и меняйте его encoding-aware инструментами; после изменения проверьте декодирование командой:

```sh
iconv -f CP1251 -t UTF-8 src/configs/hns.cfg >/dev/null
```

Не перекодируйте `hns.cfg` скрытно в рамках несвязанного изменения.

## Проверка перед завершением

Минимальный обязательный набор:

```sh
python3 -B -m unittest discover -s tests -v
openspec validate --all --strict
git diff --check
```

Дополнительно скомпилируйте `src/scripting/hns.sma` официальным `amxxpc` 1.10. В репозитории нет собственного компилятора или build wrapper, поэтому укажите в отчёте фактически использованную команду и версию.

Для изменений поведения проверьте, что:

- добавлен или обновлён регрессионный тест;
- основные OpenSpec specs описывают итоговое, а не планируемое поведение;
- README и комментарии `hns.cfg` не противоречат Cvar и коду;
- RU/EN словари имеют одинаковые ключи и placeholders;
- в diff нет случайно добавленных `.amxx`, временных файлов и изменений сгенерированных skills без причины.
