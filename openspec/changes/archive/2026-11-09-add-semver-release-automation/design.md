# Design

## Context

См. [proposal.md](proposal.md) и capability `release-versioning`. Сейчас `src/scripting/hns.sma` содержит строковый `#define VERSION "1.0"`; в репозитории нет тегов, release workflow и локального способа проверить соответствие версии артефактам. Проект компилируется официальным AMX Mod X 1.10 и не должен получать runtime-зависимость ради релизной автоматизации.

GitHub-hosted runner предоставляет Python 3 и GitHub CLI. Для создания Release требуется явное разрешение `contents: write`, а `gh release create --verify-tag` позволяет запретить неявное создание тега. Официальный релиз AMX Mod X 1.10.0.5487 предоставляет отдельные Linux-архивы base и cstrike.

Проверка этих архивов выявила, что отдельного `dhudmessage.inc` в официальной поставке нет: `set_dhudmessage` и `show_dhudmessage` объявлены непосредственно в `amxmodx.inc`. Текущее подключение legacy include из локально собранного toolchain мешает воспроизводимой официальной сборке.

## Goals / Non-Goals

**Goals:**

- сделать версию читаемой одновременно Pawn-компилятором и проверяющей автоматизацией без генерации исходника;
- одинаково проверять SemVer и структуру пакета локально и в GitHub Actions;
- публиковать только артефакты, собранные из commit, на который указывает совпадающий тег;
- ограничить write-доступ к репозиторию стадией публикации;
- оставить релизный процесс воспроизводимым из документированных команд.

**Non-Goals:**

- вычислять следующую версию из Conventional Commits или изменять её автоматически;
- обещать побитово одинаковый `.amxx` между разными версиями toolchain;
- добавлять updater в игровой сервер или сетевую проверку новых версий;
- менять plugin API, Cvar, игровые сообщения, правила раунда или состав runtime-модулей.

## Decisions

### 1. Pawn include как единственный источник версии

Добавляется `src/scripting/hns/version.inc` с одной строковой константой `HNS_VERSION`, изначально `1.0.0`. `hns.sma` подключает include и передаёт константу в `register_plugin`; прежний строковый `VERSION` удаляется либо становится алиасом без собственного значения.

Python helper извлекает ровно одно определение `HNS_VERSION` и валидирует его по SemVer 2.0.0. Он отклоняет неоднозначный файл, ведущие нули и неполные версии. README не дублирует текущий номер вручную: он ссылается на страницу Releases и описывает, где менять источник.

Альтернативы:

- корневой `VERSION` потребовал бы генерировать Pawn include перед каждой локальной компиляцией и позволил бы собрать устаревший исходник;
- версия только в Git-теге сделала бы обычную локальную сборку без тега неидентифицируемой;
- несколько констант в README/workflow оставили бы исходную проблему синхронизации.

### 2. Один stdlib-only helper для проверки и упаковки

Добавляется `scripts/release.py` без внешних Python-зависимостей. Он предоставляет отдельные команды:

- прочитать и напечатать текущую версию;
- проверить переданный тег и вернуть признак prerelease;
- собрать `hns-v<SemVer>.zip` из переданного свежескомпилированного `hns.amxx` и deployable-ресурсов;
- проверить точный список путей архива и создать `SHA256SUMS` для архива и отдельного бинарника.

Упаковка идёт по явному allowlist, а не по широкому glob всего репозитория. Конфиг копируется как bytes, поэтому его CP1251-кодировка сохраняется. ZIP содержит пути относительно `cstrike`, как требует README.

Альтернатива — shell-команды непосредственно в workflow — хуже тестируется локально, зависит от поведения разных утилит `zip` и дублирует правила структуры пакета.

### 3. Полный SemVer и тег с единственным префиксом `v`

В источнике хранится `MAJOR.MINOR.PATCH` с допустимыми SemVer prerelease/build metadata; Git-тег добавляет только `v`. Сравнение выполняется побайтово после удаления префикса, без нормализации регистра или чисел. Версия `1.0` мигрирует в эквивалентную стабильную `1.0.0`.

Если версия содержит prerelease-компонент, Release создаётся с флагом `--prerelease`. Build metadata само по себе не делает релиз предварительным.

Альтернатива — разрешить только три числа — проще, но искусственно исключает стандартные SemVer prerelease. Автоматическое повышение версии отклонено: тип MAJOR/MINOR/PATCH является продуктовым решением сопровождающего.

### 4. Fail-closed release workflow из двух jobs

`.github/workflows/release.yml` запускается только при push тега, похожего на `v*.*.*`; точную допустимость определяет helper. Workflow использует concurrency на полный ref и две стадии:

1. `build` с `contents: read`: checkout полного tagged commit, проверка версии/тега, unit tests, `git diff-tree --check`, strict OpenSpec validation, загрузка и проверка toolchain, компиляция, упаковка и передача готовых файлов через Actions artifact.
2. `publish` с `contents: write`, зависящий от успешного `build`: получение ровно этих файлов и `gh release create <tag> ... --verify-tag --generate-notes` с `GH_TOKEN`. Заголовок содержит `Hide N Seek: Ultimate <version>`; prerelease получает соответствующий флаг.

Используемые GitHub Actions закрепляются полным commit SHA с комментарием версии. Временные каталоги toolchain вычисляются внутри shell-step из стандартной переменной `$RUNNER_TEMP`: контекст `${{ runner.* }}` не используется в job-level `env`, где GitHub Actions его не разрешает. Workflow дополнительно проверяется `actionlint` до первого тега. `publish` не пересобирает плагин. Ошибка или отмена любой проверки не допускает запуск write-job. Обычный push ветки релиз не создаёт.

Альтернативы:

- сторонний release action добавил бы лишнюю supply-chain зависимость, тогда как `gh` уже установлен на GitHub runner;
- один job держал бы `contents: write` во время загрузки toolchain и выполнения тестов;
- событие `release: published` допускало бы сначала создать несогласованный Release вручную.

### 5. Закреплённый официальный AMX Mod X toolchain

Build job загружает официальные assets релиза AlliedModders `1.10.0.5487`, проверяет SHA-256 до распаковки и накладывает cstrike addon поверх base:

| Asset | SHA-256 |
| --- | --- |
| `amxmodx-1.10.0-git5487-base-linux.tar.gz` | `d82d1d65c907f358c48bdebc07e20084e7e8c4f4d0e95af275e8b43f32815c7e` |
| `amxmodx-1.10.0-git5487-cstrike-linux.tar.gz` | `6a7541a213ef71c47c1348b3457722e95669c0135c60102d5cb5a876341aa808` |

Workflow устанавливает только 32-bit runtime-библиотеки, необходимые официальному Linux `amxxpc`, и компилирует `src/scripting/hns.sma` с include из проверенного архива. URL не использует плавающий `latest`.

Перед включением workflow из `hns.sma` удаляется избыточный `#include <dhudmessage>`, а regression test запрещает его возврат. DHUD-вызовы и визуальное поведение не меняются, потому что те же natives предоставляет обязательный `amxmodx.inc`.

Альтернатива — непроверенный standalone compiler или случайный Docker image — не даёт столь прямой связи с официальным AMX Mod X. Плавающий snapshot может внезапно изменить бинарник или перестать быть доступным.

### 6. TDD для релизного контракта

До реализации добавляются Python-тесты helper и статического workflow-контракта. Они покрывают валидные стабильные/prerelease/build версии, невалидный SemVer, несовпадающий тег, точную структуру ZIP, сохранение байтов ресурсов, checksum и критичные release gates. Компиляция официальным `amxxpc` остаётся интеграционной проверкой.

Проверки не пытаются создавать реальный GitHub Release из unit tests. Фактическая публикация проверяется первым тегом `v1.0.0` после попадания workflow в `master`.

### 7. Отсутствие влияния на runtime

Изменение затрагивает только аргумент версии при `register_plugin` и compile-time include DHUD natives. Оно не добавляет AMXX events, messages, Ham hooks, Fakemeta forwards, task IDs, precache или cleanup paths. Нет логики на игрока, кадр, сообщение или entity think и, следовательно, нет измеримого runtime-влияния.

`hns.cfg`, Cvar, `hns.txt`, RU/EN-ключи и звуковые assets не меняются. Release helper копирует существующие ресурсы без перекодирования.

## Risks / Trade-offs

- [32-bit `amxxpc` перестанет запускаться на новом образе runner] → устанавливать явные i386 runtime-библиотеки и считать компиляцию обязательным gate; при необходимости менять только способ запуска, не версию toolchain.
- [Официальные assets станут недоступны] → точные URL и SHA известны; workflow завершится до публикации, а зеркалирование можно предложить отдельным change.
- [Тег отправлен до commit с workflow] → документировать порядок: сначала push commit с новой версией, затем тегировать именно его; первый `v1.0.0` создаётся только после попадания workflow в `master`.
- [Workflow оборвался во время нескольких API-запросов `gh release create`] → команда загружает assets в draft перед публикацией; повторный запуск не должен перетирать уже опубликованный Release, частичный draft очищается вручную.
- [Build metadata создаёт разные теги с одинаковым SemVer precedence] → разрешить стандарт SemVer, но документировать, что build metadata не заменяет PATCH для новой поставки.
- [Ручной Release можно создать вне workflow] → автоматизация гарантирует только Releases, создаваемые документированным процессом; защита тегов/immutable releases относится к настройкам GitHub и остаётся рекомендацией.

## Migration Plan

1. Добавить падающие regression tests для SemVer, тега, package и workflow.
2. Ввести `version.inc`, подключить его к `hns.sma` и нормализовать версию до `1.0.0`.
3. Удалить legacy `dhudmessage` include, реализовать helper, затем workflow и README; прогнать все локальные gates и официальную компиляцию.
4. Синхронизировать `release-versioning` в основные OpenSpec specs и архивировать change.
5. Отправить implementation commits в `master`, создать annotated tag `v1.0.0` на проверенном commit и отправить tag.
6. Убедиться, что GitHub Release `v1.0.0` содержит три ожидаемых assets и что checksum/структура архива корректны.

Rollback до первого тега выполняется обычным revert implementation commits. После опубликованного Release нельзя переиспользовать `v1.0.0`: исправление выпускается новой PATCH-версией; ошибочный Release можно пометить/удалить вручную, но существующий публичный тег не перемещается.
