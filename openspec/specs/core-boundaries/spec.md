# Core Boundaries Specification

## Purpose

Спецификация фиксирует назначение, совместимость и сознательные границы HNS-ядра, чтобы последующие изменения не превращали его в неуправляемую серверную сборку.

## Requirements

### Requirement: Целевая платформа

Проект SHALL оставаться Pawn-плагином для Counter-Strike 1.6 и компилироваться официальным `amxxpc` AMX Mod X 1.10 со стандартными include `amxmodx`, `fakemeta`, `hamsandwich`, `fun`, `cstrike`. DHUD natives SHALL использовать объявления из `amxmodx.inc` без зависимости от legacy `dhudmessage.inc`.

#### Scenario: Чистая сборка

- **WHEN** `src/scripting/hns.sma` компилируется AMX Mod X 1.10 с официальными include
- **THEN** создаётся loadable `.amxx` без обязательной зависимости от ReAPI, ReHLDS или сторонних include

#### Scenario: Сборка официальным release toolchain

- **WHEN** исходник компилируется base+cstrike-пакетами официального AMX Mod X 1.10.0.5487
- **THEN** компиляция не требует отсутствующего в этих пакетах `dhudmessage.inc`

### Requirement: Максимальный размер сервера

Ядро SHALL использовать стандартную модель CS 1.6 с player id 1–32.

#### Scenario: Игровое состояние хранится по player id

- **WHEN** создаются player arrays или выполняется обход игроков
- **THEN** состояние ограничено 32 слотами и очищается перед переиспользованием слота

### Requirement: Неперсистентное состояние

Ядро SHALL хранить состояние раунда и игроков только в памяти текущего процесса/карты и не обязано сохранять его в SQL, файлы или внешние сервисы.

#### Scenario: Сервер или карта перезапущены

- **WHEN** плагин загружается заново
- **THEN** AFK-состояние, личные настройки countdown и результаты предыдущих раундов не восстанавливаются

### Requirement: Отсутствие публичного plugin API

Текущее ядро SHALL не обещать публичные AMXX natives, forwards или include-контракт для сторонних плагинов.

#### Scenario: Внешний плагин расширяет сервер

- **WHEN** дополнительный плагин добавляет механику поверх HNS
- **THEN** он использует стандартные события Counter-Strike/AMXX и Cvar либо отдельный будущий согласованный API

### Requirement: Функции вне ядра

Текущее ядро SHALL не включать anti-frag, ранги/статистику, админ-меню, map chooser, автоматический баланс, blockmaker, bhop/stamina, экономику или постоянное хранилище.

#### Scenario: Требуется одна из внешних механик

- **WHEN** владелец сервера хочет такую возможность без изменения границы ядра
- **THEN** она реализуется отдельным AMXX-плагином

#### Scenario: Предлагается включение в ядро

- **WHEN** новая механика должна стать ответственностью `hns.sma`
- **THEN** OpenSpec change явно изменяет эту requirement, описывает API/производительность/совместимость и получает отдельное решение

### Requirement: Ограничение частых обработчиков

Изменения SHALL избегать необоснованной тяжёлой работы в `FM_Think`, `FM_CmdStart`, message hooks и других частых callback.

#### Scenario: Добавляется обход игроков или сущностей

- **WHEN** алгоритм выполняется на каждый кадр, input command, message или entity think
- **THEN** `design.md` обосновывает частоту, верхнюю границу операций и cleanup, а реализация получает регрессионную проверку

### Requirement: OpenSpec как процесс изменений

Любое изменение продуктового поведения SHALL начинаться с OpenSpec change и завершаться синхронизацией основной спецификации с реализованным состоянием.

#### Scenario: Исправляется баг или добавляется Cvar

- **WHEN** изменение влияет на игрока, администратора, asset, совместимость или производительность
- **THEN** до реализации создаются proposal/specs/design/tasks, а перед завершением проходят tests, AMXX compile и strict validation
